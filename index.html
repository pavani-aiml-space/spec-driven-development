Claude Code skill pack · spec-driven-development

Spec-Driven Development

A project-agnostic skill library that encodes an entire AI-DLC (AI Development Lifecycle), concept through closeout, plus the role-specific playbooks that run alongside it: what a Developer, a Product Manager, and a Technical Program Manager each produce to keep a cross-team program moving. Every skill is a standalone SKILL.md a Claude Code agent can load on its own.

01

What this is

This repo is not a single project — it is a reusable pack of Claude Code SKILL.md files, each one a self-contained playbook for one recurring piece of work. Copy the ones you need into a project's .claude/skills/, and the agent picks up the right one by name and description, no project-specific content baked in.

Every skill follows the same shape: frontmatter (name + description, the two fields Claude Code uses to decide when to trigger it), then Purpose · When to use · Process · Output · Handoff · Checklist. The Handoff section is what lets skills chain into a pipeline instead of staying a pile of disconnected checklists — see ai-dlc/writing-skills/SKILL.md for the full convention.

Dev-role skills

Artifacts a Developer produces alongside the lifecycle above — not stages of it, but the supporting record and analysis work.

roles/dev/
adr
Record a significant, hard-to-reverse technical decision — reversibility, drivers, options, consequences — as a durable record separate from the design doc.
api-contract
Before implementing a REST API, define resources, endpoints, auth, status codes, error shape, pagination, and versioning so producer and consumers agree first.
integration-spec
Force concrete engineering answers on scope, scalability, reliability, security, and rollout for a cross-team integration before a launch commitment is made.
technical-spike
A time-boxed investigation or prototype to answer a specific question when there's too much uncertainty to plan or estimate confidently.
dependency-upgrade
Evaluate and roll out an upgrade to a library, framework, or runtime safely and deliberately, rather than reactively.
runbook
Document how to operate, monitor, and troubleshoot a service — the reference handed off so someone other than the author can respond to problems.
release-notes
Diff merged PRs since the previous release, summarize by theme, and publish a dated entry to the wiki.
change-request
After release notes are published, file the formal change-management item — linked back to the release notes and source PR for audit trail.

Product Manager skills

Artifacts a PM produces: owning a roadmap across the areas they're responsible for, proving whether an initiative actually worked, and deciding whether a capability should be built or bought.

roles/product-manager/
roadmap-prioritization
Turn competing candidate initiatives, stakeholder input, and discovery findings into a prioritized roadmap — decided in an actual session, not just a scored spreadsheet.
success-metrics
Define numeric, falsifiable KPIs and OKR-style success metrics before an initiative starts, then report its actual outcome — including honest misses — afterward.
build-vs-buy
Decide whether a needed capability should be built in-house, bought, or bought-and-extended — weighing true total cost of ownership and competitive differentiation, pressure-tested with stakeholders, and closed out as a logged decision, not a gut call.
05

Technical Program Manager skills

The mechanisms a TPM uses to run a cross-team program end to end — frame it, stand up the workspace, assign ownership, and keep decisions, risk, and status honest as it runs.

roles/tpm/
◆ These are not markdown-only templates. tpm-program-space, the RACI, risk-register, decision-log, and status-update skills publish directly into a real Confluence Program Hub (and reference Jira for tracking) through the Atlassian MCP connector — the agent reads and writes the actual pages, it doesn't just draft local files for someone to copy in by hand.

Frame the program

tpm-pdlc is the map: it names the Program Management Lifecycle phases and says which single-purpose skill to run next. tpm-sdd-bridge is the handoff to the engineering lifecycle above — what crosses over, who approves, where specs live.

tpm-pdlc
Entry point for "how do we run this program?" — dual-named PMLC phases (plain + Amazon flavor), which skill runs next, human gates, and Prepare→Plan→Execute→Measure. Produces no artifacts itself.
tpm-sdd-bridge
Connects this Program Management Lifecycle to the Spec-Driven Development eng lifecycle above: what hands off, who approves, where specs live.

Concept & the Program Hub

Lock the goal and scaffold the workspace before anyone starts assigning owners.

tpm-concept
Lock business goal, vision, measurable success criteria, and in/out of scope before Align. Preferred over tpm-program-brief for new programs.
tpm-program-brief
Optional one-page Hub distill of an existing tpm-concept, for readers who won't open the full Concept doc.
tpm-program-space
Scaffold the entire Confluence space in one pass when a program is assigned — a minimal Home, a content-rich Program Hub, and every artifact page pre-filled with its own starter template. Publishes via the Atlassian MCP connector.
tpm-tooling-setup
After the Confluence space exists, set Jira (or equivalent tracker) conventions — board, epics, labels — and how work links back to the Hub.

Stakeholders & ownership

Identify who's involved before assigning accountability against that same roster.

tpm-stakeholder-map
Systematically identify every stakeholder a new (or re-scoped) program needs, prioritized by power and interest — the roster RACI and Contested Decisions assign accountability against.
tpm-raci
Define who is Responsible, Accountable, Consulted, and Informed for each deliverable or standing decision-making role when ownership is ambiguous.

Run the program

The recurring mechanisms that keep decisions, risk, and status honest while the program is live.

decision-log
Record every decision as it's made. Regular ones stay here; ones that turn out contested become a row on the shared Contested Decisions table and get linked back, never duplicated.
tpm-contested-decisions
Track and resolve decisions stalling because too many people are weighing in and nobody has final say — one Driver/Approver/Contributors/Informed row per decision.
tpm-risk-register
Identify and track program risks with a computed risk score, so they're actively managed instead of discovered only after they materialize.
status-report
A recurring, honest update on progress, health, milestones, and blockers. Rolls up into the biweekly stakeholder update when items are at risk and have a mitigation.
tpm-biweekly-stakeholder-update
A senior-stakeholder update: a recommendation, one decision table to review, progress/demos as evidence, and next-two-weeks commitments. Preferred over status-report for sponsor-level audiences.
06

Design principles

No project-specific content
Every skill applies to any AI-driven application, not just the one that inspired it.
Consolidated, not duplicated
Overlapping skills from different source projects (e.g. audit / code-review / pr-review) were merged into one canonical skill instead of kept as near-duplicates.
Each skill states its handoff
The Handoff section says what feeds in and what it feeds out to, so the pack composes into a full lifecycle rather than staying a set of disconnected checklists.
